Post-Mortem: Tailscale MagicDNS Hijack & Layer 3 vs Layer 7 Triage

"Internet is down... but 1.1.1.1 works?"

A real-world debugging investigation where DNS queries timed out across all applications while raw TCP/IP routing was 100% operational. Uncovering how Tailscale's virtual network interface (utun5) silently seized system resolver priority (order 104200) on macOS.

Layer 3 (IP Routing)
1.1.1.1:443 UP

TCP connection succeeded

Layer 7 (DNS Resolver)
google.com TIMED OUT

getaddrinfo failed

Root Culprit
utun5 (MagicDNS)

Order 104200 override

The Detective Story Step-by-Step

How the diagnostic breadcrumbs led directly from symptom to root cause

1

The Outage Symptoms

Commands like nslookup google.com and dig api.anthropic.com completely timed out. Websites would not load in browsers.

;; connection timed out; no servers could be reached
2

The Eureka Clue: IP vs Domain

Testing direct TCP connection to IP 1.1.1.1 succeeded instantly. But testing hostname google.com failed on getaddrinfo.

$ nc -zv 1.1.1.1 443 → Connection succeeded!
$ nc -zv google.com 443 → getaddrinfo: nodename nor servname provided
3

The Red Herring: Wi-Fi DNS Settings

Running sudo networksetup -setdnsservers "Wi-Fi" 1.1.1.1 8.8.8.8 did not fix the problem because macOS uses a dynamic resolver hierarchy managed by scutil rather than standard Wi-Fi adapter DNS when VPN tunnels are active.

4

The Unmasking via `scutil --dns`

scutil --dns exposed that Tailscale's utun5 virtual adapter had registered 100.95.0.251-254 as Resolver #1 with Order 104200, forcing all DNS queries through Tailscale's MagicDNS.

5

The Fix & Instant Recovery

Toggling Tailscale OFF in the macOS menubar UI immediately destroyed the utun5 interface, unregistering Resolver #1. Standard Wi-Fi DNS resumed, and nc -zv google.com 443 succeeded right away!

Interactive Triage Decision Tree

Follow the 3-step test sequence to isolate any network connectivity problem in seconds

TEST 1: Layer 3

Can you reach direct IPs?

Test raw IP communication bypassing the DNS subsystem.

nc -zv 1.1.1.1 443
Fails: Wi-Fi / Router / Gateway issue.
Passes: Network is UP! Proceed to Test 2.
TEST 2: Layer 7

Does DNS resolve?

Test hostname lookup through system resolver libraries.

nc -zv google.com 443
Fails: DNS Outage! Proceed to Test 3.
Passes: Full connectivity is healthy.
TEST 3: Resolver Order

Who owns Resolver #1?

Inspect macOS DNS hierarchy to find VPN overrides.

scutil --dns | grep -A 8 "resolver #1"
100.95.0.x / utun*: Tailscale MagicDNS lock.
Fix: Disable MagicDNS or toggle VPN.

Diagnostic & Repair Scripts

Ready-to-use scripts included in this repository to automate diagnosis and recovery

check-connectivity.sh

Runs all 6 checks: Default route, L3 direct IP, L7 DNS resolution, scutil DNS hierarchy, and Tailscale client status.

./check-connectivity.sh 
# Run directly from repo:
chmod +x check-connectivity.sh
./check-connectivity.sh

# Or run instantly via curl:
curl -sSL https://raw.githubusercontent.com/rifaterdemsahin/connectivity-checker/main/check-connectivity.sh | bash
fix-tailscale-dns.sh

Locates macOS Tailscale binary, resets DNS overrides (--accept-dns=false), flushes macOS mDNS cache, and verifies connectivity.

./fix-tailscale-dns.sh 
# Run reset utility:
chmod +x fix-tailscale-dns.sh
./fix-tailscale-dns.sh

# Flush macOS DNS cache manually:
sudo dscacheutil -flushcache
sudo killall -HUP mDNSResponder

How to Prevent Future Outages

Configuration best practices for Tailscale on macOS

1. Add CLI Path Alias

The macOS App Store version installs the binary inside the app bundle. Add an alias in your ~/.zshrc:

alias tailscale="/Applications/Tailscale.app/Contents/MacOS/Tailscale"

2. Disable MagicDNS Override

If your Tailscale network doesn't need to override public internet DNS, start Tailscale with DNS bypass:

tailscale up --accept-dns=false

3. Tailscale Admin Console

In your Tailscale Admin Console (DNS Settings), configure public fallback DNS servers (like 1.1.1.1 and 8.8.8.8) to prevent deadlocks when nodes are offline.
